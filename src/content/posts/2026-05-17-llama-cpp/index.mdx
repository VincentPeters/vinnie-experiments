## What llama.cpp actually is

llama.cpp's job is small and specific. Load a model file from disk, turn prompts into tokens, send tokens back. That's it. No UI, no memory between sessions, no orchestration. Knowing exactly where the runtime stops is what makes the rest of the tour make sense.

A token, in case the word is new, is roughly a word fragment. "Weather" might be one token, "weatherman" might be two. The model produces them one at a time. The "streaming" text you see in a chat UI is just tokens arriving as they're generated.

<aside class="marginalia">

words to keep straight.

*model* = the GGUF file on disk.

*runtime* = llama.cpp, the thing that loads weights and produces tokens.

*wrapper* = whatever calls the runtime (your script, a chat UI, an agent loop).

"i'm using Llama" can mean any of the three, and each layer has different failure modes.

</aside>

When people say "I'm using Llama", they could mean three different things: the *model* (the GGUF file on disk), the *runtime* (llama.cpp, the program that loads the file and produces tokens), or the *wrapper* (the code calling the runtime: a Python script, a chat UI, an agent loop). The rest of this post is precise about which is which.

<aside class="marginalia">

GGUF is the file format. one binary blob holding model weights plus a metadata header (tokenizer, prompt template, quantization scheme).

single-file means single-command download. no python env, no transformers install, no five-file dance.

</aside>

The model itself lives in a GGUF file. One binary blob, weights plus metadata. That single-file design is why llama.cpp can install in one command and pull a model in one more.

<aside class="marginalia">

quantization, briefly.

the trained weights are 16-bit floats. Q4_K_M shrinks them to ~4.5 bits per weight by grouping similar values and storing them as offsets from a small set of "anchor" values (K-means style).

the M variant spends slightly more bits on the layers that matter most. the file gets ~4× smaller but the model still mostly knows what it knew.

</aside>

Models are big. The 8B Llama 3.1 weights are about 16 GB in their original 16-bit form, too much for a typical laptop. Quantization is how you shrink them. Each weight gets stored in fewer bits, 4 instead of 16, using clever grouping so the model still mostly works. Q4_K_M is the variant we'll use today: ~4.6 GB on disk, decent quality. More on the tradeoff in the showcase.

And a few things llama.cpp deliberately doesn't do, so you stop looking for them:

- It won't pick a model for you. You bring the GGUF, it runs it.
- It won't route tool calls. You can prompt for JSON, but anything fancier (function calling, MCP, agent loops) belongs to a wrapper.
- The server is stateless. Every request carries its own conversation history; tracking that history is the client's job.
- It won't fine-tune. That's a different binary (`llama-finetune`) and a different post.

That smallness is the point. The runtime does one thing well, which means anything built on top stays swap-friendly.

## How to set it up


Pinned: llama.cpp **b9095** (10 May 2026). Model: `bartowski/Meta-Llama-3.1-8B-Instruct-GGUF` at Q4_K_M.

```powershell title="Windows"
winget install llama.cpp
```

```bash title="macOS / Linux"
brew install llama.cpp
```

```powershell title="Verify"
llama-cli --version
```

![terminal output of `llama-cli --version` showing build b9095](./verify.png)

Now pull a model and start talking to it.

```powershell title="Run model"
llama-cli -hf bartowski/Meta-Llama-3.1-8B-Instruct-GGUF -cnv -p "You are a curt 19th-century lighthouse keeper. Reply in two sentences max."
```

`-hf <repo>` lets llama-cli act as its own downloader, so you skip the manual "fetch GGUF, place it somewhere, point at it" routine.
`-cnv` is conversation mode.
`-p` is the system prompt.

First run pulls the model (~4.6 GB) and caches it under `%USERPROFILE%\.cache\llama.cpp\`. Every run after that is instant.

<video src={lighthouse} controls autoplay loop muted playsInline preload="metadata" aria-label="TUI"></video>

For an OpenAI-compatible local API instead:

```powershell title="Run as Api"
llama-server -hf bartowski/Meta-Llama-3.1-8B-Instruct-GGUF --port 8080
```

`http://localhost:8080` gives you a chat UI in the browser. `POST http://localhost:8080/v1/chat/completions` gives you the API.

## What can we do with this?

Four things, each useful on its own.

### Prompts as personalities

Start with `-cnv` and a system prompt. The model's personality is downstream of one line of text. Type "you are a 19th-century lighthouse keeper who answers in two sentences" and the next ten replies arrive with weight, faint grumpiness, and ocean somewhere in the mid-distance. Change the prompt and restart; the new character shows up immediately. No fine-tuning, no training data, no new model file. Just words.

> **[VISUAL]** short screen recording (gif, 5–10 seconds) of typing two or three messages to the lighthouse keeper and getting answers back. captures the immediacy in a way a static screenshot can't.

### A model in a pipe

Without `-cnv`, llama-cli behaves like a Unix filter. Text in, text out.

```bash
llama-cli -m model.gguf -p "summarise:" < article.txt > summary.txt
```

Swap "summarise" for "extract every email address", "translate to Dutch", or "rate this email's politeness from 1 to 10". Same shape, different output. Pair it with `find` or a `for` loop and you've automated something that needed a paid API two years ago.

> **[VISUAL]** stacked-pane terminal screenshot. top pane: a longish article (visible scrollback). bottom pane: a short summary coming back. labels "in" and "out" on the side if it helps.

### Anything-that-knows-OpenAI knows this

`llama-server` is the bigger move. It exposes the same model as an OpenAI-compatible HTTP endpoint, so any client that can call OpenAI can call your laptop. Point the OpenAI Python SDK at `base_url=http://localhost:8080/v1`, leave the API key empty, and it works.

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8080/v1", api_key="not-needed")
client.chat.completions.create(
    model="local",
    messages=[{"role": "user", "content": "Why is the sky blue?"}]
)
```

The rest of this tour leans on this trick. Gradio chat UIs, agent loops, RAG demos: same code as the hosted version, with `localhost:8080` swapped in for the OpenAI host.

> **[VISUAL]** split-screen. left: the python snippet running. right: llama-server's log lines lighting up as the request hits. makes "your laptop is the backend" visible instead of theoretical.

### The quality dial

The same 8B model lives at roughly 4.6 GB at Q4_K_M, 3.4 GB at Q3_K_M, 6.4 GB at Q5_K_M. Lower the bits, lower the RAM, lower the quality. The curve isn't linear, though. Q4_K_M is where most people stop because dropping to Q3 starts to sound subtly off in long answers, and Q5 isn't usually audible. Default to Q4_K_M. Push down only when you have to fit in less RAM. Push up only when you can actually hear the difference.
